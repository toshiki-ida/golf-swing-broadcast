# 学習ベースのクラブヘッド検出への移行 — 調査メモ (未実装)

日付: 2026-10-21 / 対象ブランチ: `feature/ai-analysis`
前提: 商用利用・配布可能なライセンスのみ (Apache-2.0 / MIT / BSD)。AGPL の Ultralytics (YOLOv5/8/11) は使わない。
推論は ONNX Runtime (CPU) で exe に同梱。学習はこの PC (RTX 3050 Laptop, VRAM 4 GB) で行う。

> ここに書いた数値のうち「見積もり」は、公開情報と本リポジトリの実測 (MediaPipe の処理時間、exe サイズ) からの推定で、
> 実際に学習・推論して確かめたものではない。確認が必要な項目には (要確認) を付けた。

## 1. 候補モデル

| モデル | ライセンス | パラメータ / ONNX サイズ | CPU 推論の目安 (416〜640 入力) | 備考 |
|---|---|---|---|---|
| **YOLOX-Nano** (Megvii) | Apache-2.0 | 0.9 M / 約 4 MB | 10〜20 ms/frame (要確認) | 小物体向けに入力 640 以上が必要。学習コードも Apache-2.0 |
| **YOLOX-Tiny** | Apache-2.0 | 5.1 M / 約 20 MB | 25〜50 ms/frame (要確認) | 精度と速度の中間。第一候補 |
| YOLOX-S | Apache-2.0 | 9.0 M / 約 36 MB | 60〜120 ms/frame | 4 GB VRAM でも batch 8 で学習可 |
| **RT-DETR** (lyuwenyu, R18) | Apache-2.0 | 20 M / 約 80 MB | 150 ms 以上 (CPU では重い) | NMS 不要で小物体に強いが、CPU 推論と 4 GB 学習が厳しい |

| Ultralytics YOLOv8/11 | AGPL-3.0 | — | — | **除外** |

推奨: **YOLOX-Tiny を 1 クラス (clubhead) で学習**し、ONNX (opset 11) に変換して ONNX Runtime CPU で推論。
精度が足りなければ YOLOX-S、速度を詰めるなら YOLOX-Nano に変更する (同じ学習コード・同じデータで切り替えられる)。

クラブヘッドは 1080p でも 10〜25 px の小物体で、ダウンスイングでは残像 (筋) になる。
全画面を 640 に縮小すると 5 px 以下になり検出できないため、**手首を中心にした ROI (身長代替値 ×2.4 の正方形) を 640 に切り出して推論**する。
ROI は既存トラッカーの骨格 (MediaPipe) から取れる。

## 2. 学習データ

### 現状のラベル数

| 出所 | 枚数 | 備考 |

### 必要枚数の見積もり

- 1 クラス・小物体・背景が多様 (ゴルフ場、ギャラリー、練習場) の検出器を事前学習済み (COCO) から fine-tune する場合、
  経験的には **500 枚で動く、2,000 枚で実用、5,000 枚以上で安定** (要確認: 本タスクでの実測なし)。
- 1 クリップから使えるのは局面の異なる 20〜40 フレーム (連続フレームは似すぎるので 0.1 秒おき程度)。
  **2,000 枚 ≒ 60〜80 クリップ** 分。今ある実収録 21 本では 500〜800 枚が上限。
- 残像 (ダウンスイングの筋) は「ヘッド」と別クラス (`clubhead_blur`) にするか、筋の先端にボックスを置くかを決めてからラベルする。
  既存トラッカーは「筋の先端 = ヘッド」として扱っているので、同じ定義にする。

### ラベルの作り方 (提案)

1. `tools/label_club.py` を拡張し、1 点クリック → 固定サイズ (ヘッド径 ×1.6) のボックスを書く。6 局面ではなく 0.1 秒おきに付ける。
2. 既存トラッカーの高信頼度点 (手元接続あり・連続性あり) を **候補として表示し、人が OK / 修正 / 削除** する半自動ラベリング。
   確認済みの点だけを学習に入れる (`corrections.json` の `source: auto` で人が触らなかった点 = 確認済みとみなす)。
3. ラベルは COCO 形式 (`annotations/clubhead_train.json`) に書き出すツールを `tools/export_coco.py` として用意する。

## 4. ONNX Runtime (CPU) での推論: exe サイズと処理時間の見積もり

| 項目 | 見積もり |
|---|---|
| `onnxruntime` (CPU) wheel | 約 15〜20 MB → exe +20 MB 程度 (要確認: DirectML 版は +50 MB) |
| モデル (YOLOX-Tiny ONNX) | 約 20 MB (FP32)。FP16 / INT8 量子化で 5〜10 MB |
| 推論時間 (ROI 640×640, CPU 4 コア) | YOLOX-Tiny 25〜50 ms/frame、Nano 10〜20 ms (要確認) |
| 1 クリップ (HFR 2x、300 フレーム) | Tiny で 8〜15 秒。現在の MediaPipe (20 ms/frame) + 差分探索 (30〜60 秒) に対して同程度か短い |
| exe 全体 | 現在 904 MB (ffmpeg full 455 MB 込み) → +40 MB 程度 |

ffmpeg を essentials ビルドに替えれば exe は 500 MB 台になるので、検出器の追加分は誤差の範囲。

## 6. 既存 club_tracker との組み合わせ (構成案)

```
フレーム ─ MediaPipe Pose ─ 手首中点・身長代替値 ─┐
                                                  ├─ ROI (手首中心 2.4×身長) ─ 検出器 (ONNX) ─ ヘッド候補 [(x, y, score), ...]
                                                  │
                                                  └─ 現行の候補生成 (動き差分 + シャフト線分) ─ ヘッド候補 [(x, y, score), ...]
                                                                      ↓
                                    候補の統合: 検出器の score を 0〜1 で正規化して既存の score に加算 (重み 1.0)
                                                                      ↓
                                    時間的連続性の判定 (既存のまま): 移動量上限・向きの予測・追跡開始条件・欠損・区間分割・信頼度ゲート
```

- 検出器は **候補の提案だけ** を担当し、「どの候補を採用するか」「欠損・区間・信頼度」は既存のロジックをそのまま使う。
  → 検出器の有無で出力の形 (`ClubTrackResult`) が変わらず、編集タブ・縦型書き出し・評価ツールに影響しない。
- 検出器が無い (ONNX が同梱されていない / 読めない) ときは現行どおり動く (遅延 import + try/except)。
- 手元接続率 (`attached`) の定義: 検出器の候補が採用されたフレームも「接続あり」とみなす (検出器は背景を見ないよう ROI で絞っているため)。
- 評価は `tools/eval_club.py --all --split tune` の枠組みをそのまま使い、`--tag det_1` 等で before/after を残す。

## 7. 進め方 (提案)

| 段階 | 内容 | 目安 |
|---|---|---|
| 0 | ラベル定義 (ヘッド中心 + 固定ボックス、残像は先端) をオーナーと合意 | — |
| 1 | `label_club.py` を 0.1 秒おき・半自動 (トラッカー候補の OK/修正) に拡張、COCO 書き出し | 1 日 |
| 2 | 実収録 21 本 + 手持ち 6 本で 500〜800 枚ラベル | オーナー作業 2〜4 時間 |
| 3 | YOLOX-Tiny を fine-tune (開発 PC)、ONNX 変換、ROI 推論の検証 | 1〜2 日 |
| 4 | `ai/club_detector.py` (ONNX Runtime) を候補提案として club_tracker に接続、tune で before/after | 1 日 |
| 5 | holdout で確認、spec に onnxruntime とモデルを追加 | 半日 |

学習データが 500 枚に満たない段階では、検出器より **ラベル付け支援 (半自動ラベリング)** の方が投資効果が高い。
