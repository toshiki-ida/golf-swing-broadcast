推奨: **YOLOX-Tiny を 1 クラス (clubhead) で学習**し、ONNX (opset 11) に変換して ONNX Runtime CPU で推論。
精度が足りなければ YOLOX-S、速度を詰めるなら YOLOX-Nano に変更する (同じ学習コード・同じデータで切り替えられる)。

クラブヘッドは 1080p でも 10〜25 px の小物体で、ダウンスイングでは残像 (筋) になる。
全画面を 640 に縮小すると 5 px 以下になり検出できないため、**手首を中心にした ROI (身長代替値 ×2.4 の正方形) を 640 に切り出して推論**する。
ROI は既存トラッカーの骨格 (MediaPipe) から取れる。

### 必要枚数の見積もり

- 1 クラス・小物体・背景が多様 (ゴルフ場、ギャラリー、練習場) の検出器を事前学習済み (COCO) から fine-tune する場合、
  経験的には **500 枚で動く、2,000 枚で実用、5,000 枚以上で安定** (要確認: 本タスクでの実測なし)。
- 1 クリップから使えるのは局面の異なる 20〜40 フレーム (連続フレームは似すぎるので 0.1 秒おき程度)。
  **2,000 枚 ≒ 60〜80 クリップ** 分。今ある実収録 21 本では 500〜800 枚が上限。
- 残像 (ダウンスイングの筋) は「ヘッド」と別クラス (`clubhead_blur`) にするか、筋の先端にボックスを置くかを決めてからラベルする。
  既存トラッカーは「筋の先端 = ヘッド」として扱っているので、同じ定義にする。

### ラベルの作り方 (提案)

1. `tools/label_club.py` を拡張し、1 点クリック → 固定サイズ (ヘッド径 ×1.6) のボックスを書く。6 局面ではなく 0.1 秒おきに付ける。
2. 既存トラッカーの高信頼度点 (手元接続あり・連続性あり) を **候補として表示し、人が OK / 修正 / 削除** する半自動ラベリング。
   確認済みの点だけを学習に入れる (`corrections.json` の `source: auto` で人が触らなかった点 = 確認済みとみなす)。
3. ラベルは COCO 形式 (`annotations/clubhead_train.json`) に書き出すツールを `tools/export_coco.py` として用意する。

## 4. ONNX Runtime (CPU) での推論: exe サイズと処理時間の見積もり

| 項目 | 見積もり |
|---|---|
| `onnxruntime` (CPU) wheel | 約 15〜20 MB → exe +20 MB 程度 (要確認: DirectML 版は +50 MB) |
| モデル (YOLOX-Tiny ONNX) | 約 20 MB (FP32)。FP16 / INT8 量子化で 5〜10 MB |
| 推論時間 (ROI 640×640, CPU 4 コア) | YOLOX-Tiny 25〜50 ms/frame、Nano 10〜20 ms (要確認) |
| 1 クリップ (HFR 2x、300 フレーム) | Tiny で 8〜15 秒。現在の MediaPipe (20 ms/frame) + 差分探索 (30〜60 秒) に対して同程度か短い |
| exe 全体 | 現在 904 MB (ffmpeg full 455 MB 込み) → +40 MB 程度 |

ffmpeg を essentials ビルドに替えれば exe は 500 MB 台になるので、検出器の追加分は誤差の範囲。

## 6. 既存 club_tracker との組み合わせ (構成案)

```
フレーム ─ MediaPipe Pose ─ 手首中点・身長代替値 ─┐
                                                  ├─ ROI (手首中心 2.4×身長) ─ 検出器 (ONNX) ─ ヘッド候補 [(x, y, score), ...]
                                                  │
                                                  └─ 現行の候補生成 (動き差分 + シャフト線分) ─ ヘッド候補 [(x, y, score), ...]
                                                                      ↓
                                    候補の統合: 検出器の score を 0〜1 で正規化して既存の score に加算 (重み 1.0)
                                                                      ↓
                                    時間的連続性の判定 (既存のまま): 移動量上限・向きの予測・追跡開始条件・欠損・区間分割・信頼度ゲート
```

- 検出器は **候補の提案だけ** を担当し、「どの候補を採用するか」「欠損・区間・信頼度」は既存のロジックをそのまま使う。
  → 検出器の有無で出力の形 (`ClubTrackResult`) が変わらず、編集タブ・縦型書き出し・評価ツールに影響しない。
- 検出器が無い (ONNX が同梱されていない / 読めない) ときは現行どおり動く (遅延 import + try/except)。
- 手元接続率 (`attached`) の定義: 検出器の候補が採用されたフレームも「接続あり」とみなす (検出器は背景を見ないよう ROI で絞っているため)。
- 評価は `tools/eval_club.py --all --split tune` の枠組みをそのまま使い、`--tag det_1` 等で before/after を残す。

## 8. 実装 (2026-10-21) — 蓄積・学習・推論の経路を先に通した

§7 の段階 1〜5 を「データが少なくても経路だけは全部動く」形で先に実装した。モデルは §1 の候補ではなく、
まず **自前の小さなヒートマップ回帰 CNN (0.17M パラメータ、ONNX 0.68 MB)** にした。理由は (a) 外部重みを使わないので
ライセンスの確認が不要、(b) 入出力 (手首中心の切り出し → ヒートマップのピーク) が `ai/club_detector.py` に閉じているので、
データが貯まったら YOLOX-Nano/Tiny (Apache-2.0) に差し替えても呼び出し側は変わらない。

### 8.1 ラベルの蓄積 (`ai/dataset.py`)

| 保存契機 | 送出用書き出し (`app._do_edit_export` を `ai/edit_hook.py` が包む) と縦型書き出し。どちらも書き出し完了後 |
|---|---|
| 強ラベル | 制御点のうち manual (人が置いた / 動かした) と auto_confirmed (自動生成のまま承認)。`corrections.json` で区別 |
| 弱ラベル | 制御点間のスプライン補間点を 0.1 秒おきに interpolated として保存。既定では学習に使わない (`--use-weak`) |
| 画像 | 手首中点を中心にした正方形 (一辺 2.4×身長代替値、フレームに収まるよう制限) を 320 px に縮小した JPEG |
| 記録 | frame (in_frame 基準) / abs_frame / x, y (元解像度) / 切り出し枠と枠内座標 / 画像サイズ / labeler / 保存日時 |
| 除外 | `tests/real/split.yaml` の holdout。再書き出しはフォルダごと上書き |
| 既存ラベル | `tools/import_labels.py` が `tests/club_labels.json` を同じ形式で取り込む。骨格が無いので MediaPipe (画像モード) で手首を求めて切り出す |

GUI 結合テスト (rec_0611_162655, 自動生成 → 1 点移動 + 1 点追加 → 縦型書き出し → 送出用書き出し):
strong 19 (manual 2 / auto_confirmed 17) + weak 1、画像 20 枚、2 回目の書き出しで上書きされることを確認。

### 8.2 学習 (`tools/train_clubhead.py`)

- 入力 256×256 (RGB 0〜1)、出力 64×64 ヒートマップ (stride 4)、CenterNet 型 focal loss、AdamW + cosine。
- 分割はクリップ単位 (`--val-clips 1`)。データが少ないときは `--min-steps 1500` に届くまで epochs を自動で増やす。
- 実装中に直した点: ヒートマップの中心を整数画素に丸めてピークを正確に 1 にする (丸めないと正例が 0 個になり学習しない)、
  最終層バイアスを事前確率 0.01 で初期化 (背景 4096 画素に対し正例 1 画素)。
- 出力: `models/clubhead.onnx` (opset 13) と `models/clubhead_train.json`。

### 8.3 推論 (`ai/club_detector.py` → `ai/club_tracker.py`)

- ONNX Runtime CPU (intra_op 2 スレッド)。`models/clubhead.onnx` が無い・読めない・onnxruntime が無い場合は `available()=False` で従来方式。
- `track_club(use_detector=None)`: 検出器の 3×3 極大 (score ≥ 0.25、上位 3 個) を kind="det" の候補として既存の候補列に追加。
  手首からの距離が探索環 [r_min, r_max] の外、または除外マスク上の候補は捨てる。採用・連続性・欠損・区間・信頼度は従来と同じ。
- `tools/run_club_tracker.py --detector | --no-detector`、`tools/eval_club.py --detector off|on|both` (both = 1 つの表に両方の行)。
- exe: `GolfSwingBroadcast.spec` に `collect_all('onnxruntime')` と `models/` 同梱を追加 (CI の onefile は hidden-import のみ)。

### 8.4 1 回目の学習と tune での比較 (2026-10-22)

**学習に使えるラベル**: `tests/club_labels.json` 由来の 12 点 (sample_30fps 6 / IMG_1095_1080p 6、いずれも Claude の目視) + 弱ラベル 32 点。
実収録素材のラベルはまだ無い (オーナーの書き出しで貯まる)。

**学習 (`models/clubhead_train.json`)**: クリップ単位分割で学習 6 点 / 検証 6 点、1500 ステップ、RTX 3050 で 135 秒。

| | 平均 px | 中央値 px | PCK@15 | PCK@30 |
|---|---|---|---|---|
| 学習クリップ (sample_30fps) | 7.7 | 6.9 | 1.00 | 1.00 |
| 検証クリップ (IMG_1095) | 457 | 251 | 0.00 | 0.00 |

→ 6 点を丸暗記しただけで汎化はしていない。経路が通ったことの確認であって、精度の評価ではない。

**tune 11 本の比較 (`tests/real/results/20261022_0730_det_1_tune_283432d+dirty.md`, 検出器の候補を「手元接続あり」として扱った版)**

| 記録 | 平均観測率 | ゲート通過 | 一致 (22 中) |
|---|---|---|---|
| 従来方式 (det off) | 39% | 9 / 11 (130128・162742 が不通過) | 3 |

検出器の候補を接続ありに数えたせいで信頼度ゲートを通過してしまった** (誤った通過)。

→ `det_2`: 検出器の候補は手元接続に数えず、追跡開始も motion の遠方塊と同じ「2 フレーム連続で同じ向き・距離」に限定した。
結果は本節の末尾に追記する。

**結論 (現時点)**: 検出器は学習データが 12 点では精度を語れない。ただし蓄積 → 学習 → ONNX 推論 → 評価の経路は通ったので、
オーナーが編集タブで軌道を承認して書き出すたびに `datasets/clubhead/` が増え、`tools/train_clubhead.py` を回し直すだけで更新できる。
500 点を超えたら §1 の YOLOX-Nano/Tiny への差し替えを検討する。

**det_2 (`tests/real/results/20261022_0747_det_2_tune_283432d+dirty.md`, 検出器の候補を接続ありに数えない版)**

| 従来方式 (det off) | 39% | 9 / 11 | 3 | 130128・162742 が不通過 |

- 代わりに 162742 (目視では正しい) と 161732 が不通過になった。検出器の候補は接続ありに数えないので、
  検出器で増えた観測の分だけ手元接続率が薄まるため。学習データが増えて検出器を信用できるようになったら、
  score の高い検出候補だけ接続ありに数える (閾値はオーナーのラベルで決める) のが次の一手。
- 処理時間は従来と同程度 (+ONNX 推論 1 フレームあたり数 ms)。
- **現状の既定**: `models/clubhead.onnx` があれば検出器を使う。モデルは .gitignore 済みなので他の PC では従来方式のまま。
  この PC で従来方式に戻すときはモデルを退避するか `--no-detector`。holdout は未実行。
