# golf-swing-broadcast｜SRT 入出力・リモート運用 検討

作成日: 2026-08-10

---

## 1. 基本方針

**SRT の変換は汎用のエンコーダ / デコーダ機材に任せ、アプリ本体は現行の SDI 入出力のまま使う。**

- アプリから見れば入出力は今までどおり DeckLink の SDI。**ソフト改修は不要**
- SRT のチューニング（latency・再送・暗号化・再接続）は機材側の実績ある実装に任せられる
- 障害の切り分けが「機材か、アプリか」で明確に分かれる
- トレードオフ: 機材コストと、現場に置く箱が増えること

---

## 2. 全体構成

```
【現場】                          【インターネット / 回線】        【中継先・局】

カメラ ─SDI─▶ SRTエンコーダ ═════════ SRT ═════════▶ SRTデコーダ ─SDI─▶ 本アプリ
                                                                            │
                                                                     (収録・軌道編集)
                                                                            │
   局へ ◀─SDI─ SRTデコーダ ◀════════ SRT ═════════ SRTエンコーダ ◀─SDI─────┘
```

アプリの入口 = DeckLink SDI IN、出口 = DeckLink SDI OUT のまま変わらない。

---

## 3. 系統パターン

| パターン | 構成 | 必要機材 | 用途 |
|---|---|---|---|
| **A. 入力のみ SRT** | 遠隔カメラ → SRT → デコーダ → アプリ | エンコーダ×1 / デコーダ×1 | 現場に人を出さずに素材を受ける |
| **B. 出力のみ SRT** | アプリ → エンコーダ → SRT → 局 | エンコーダ×1 / デコーダ×1 | 完成尺を IP で送る |
| **C. 双方向** | A + B | エンコーダ×2 / デコーダ×2 | フル IP 運用 |
| **D. SDI 主系 + SRT 副系（推奨スタート）** | 本線は SDI、SRT は確認用・バックアップ | エンコーダ×1 / デコーダ×1 | リスク最小で段階導入 |

## 5. 検討事項

### 5.1 遅延バジェット

| 要素 | 目安 |
|---|---|
| SRT latency 設定 | **RTT × 2.5〜4**（LAN 20–40ms / 同一都市 120–200ms / 遠距離・モバイル 500–1000ms） |
| エンコード（低遅延モード） | 30–100 ms |
| デコード | 30–80 ms |
| アプリの DeckLink 出力 preroll（既存 4 frames） | 約 66 ms |

- **用途で許容値が変わる。先に決めるべき最重要項目。**
  - 「確認用モニタ」なら片道 1 秒でも可
  - 「オペレータが SRT 映像を見て CUE を打つ」なら往復遅延がそのまま操作感になる
- latency を下げすぎるとロスを再送で救えなくなる。**遅延と安定性はトレードオフ**

### 5.2 ネットワーク・接続モード

- **caller / listener / rendezvous** はどちら側がグローバル IP を持つかで決まる
  - listener 側は **UDP ポート開放**が必須
  - 双方 NAT 配下なら rendezvous、または中継サーバを立てる
- 帯域は **送出ビットレート × 1.25〜1.5**（再送分のヘッドルーム）
- 回線二重化（ボンディング）は SRT 単体では不可 → 対応機材 / ゲートウェイが必要
- 暗号化: passphrase（AES-128/256）。複数ストリームを 1 ポートに束ねるなら streamid

### 5.3 画質・ビットレート

- 本アプリの**軌道オーバーレイは細線＋グラデーション**で、低ビットレートだと真っ先に潰れる
- 1080 で **8–15 Mbps、CBR 推奨**（VBR はバースト時にロスを誘発）
- H.264 か HEVC か。HEVC は同画質で帯域 6〜7 割だが、対向機の対応が前提

### 5.4 フォーマット整合（要注意）

- 系統全体を **1080i59.94 で統一するか、1080p59.94 で統一するか**を先に決める
- 機材が勝手に i↔p 変換すると、アプリ側のデインタレース処理と二重になり画質が落ちる
- フレームレート 59.94 / 60 の取り違えは、じわじわコマ飛びになるので注意

### 5.5 音声

- 現状アプリは**映像のみ**を扱う（録画・書き出しに音声トラックなし）
- 音声を運ぶ場合は SRT の MPEG-TS に載せ、**アプリを迂回して**局側へ渡す構成にする
- または音声だけ既存回線で別送りにする

### 5.6 タイムコード

- SDI の VITC / LTC は機材が対応していないと SRT で運ばれない
- 複数カメラを SRT で受ける場合、**フレーム同期は保証されない**（genlock も効かない）

### 5.7 障害時の挙動

- SRT が切れると**デコーダ出力が黒画 or 静止**になる。どちらの挙動か機材仕様を確認
- **アプリ側の既存挙動に注意**: `DeckLinkInput` は入力フレームが 3 秒届かないと
  自動でテストパターンにフォールバックする（`FRAME_TIMEOUT_SEC = 3.0`）。
  SRT 断で SDI が無信号になるとこれが発動する。**望む挙動か要確認**
- 復旧手順（誰が・どこで・どう再接続するか）を運用として決めておく
- SDI 主系を残す（パターン D）のが最も確実な保険

### 5.8 設置・電源・監視

- 現場側は無人になりがち。**電源断からの自動復帰**、UPS、遠隔での再起動手段
- 機材の Web UI に遠隔から到達できるか（VPN 経由）
- 回線の生死・ビットレート・ロス率をどこで監視するか

## 6. アプリ側で必要な対応

**基本は改修ゼロ。** ただし以下は確認・調整が要る。

| 項目 | 内容 |
|---|---|
| 入力断時のフォールバック | 3 秒でテストパターンに落ちる挙動（`decklink_io.py` `DeckLinkInput.FRAME_TIMEOUT_SEC`）。SRT 断と相性を確認 |
| 入力フォーマット | 1080i59.94 前提。デコーダ出力と一致しているか |
| 出力 preroll | DeckLink 出力の 4 frames は遅延計算に含める |
| 収録品質 | SRT で一度圧縮された映像を再収録するため、二重圧縮になる。CRF 設定の見直し |

## 7. リモートデスクトップ運用（映像を送らず「操作」だけ遠隔にする案）

SRT とは別軸の選択肢。**現場PC（アプリ＋DeckLink＋SDI）はそのまま現場に置き、オペレータだけ遠隔から画面操作する。**

- 長所: 映像経路は現行 SDI のまま = **遅延・画質・タイムコードの問題が発生しない。機材追加も実装もゼロ**
- 短所: 操作レスポンスが回線依存。プレビュー動画の追従が悪い。ShuttlePRO が使えない

### 7.1 ツール比較

| ツール | 動画プレビューの追従 | コスト | 備考 |
|---|---|---|---|
| **Windows 標準 RDP** | 弱い。1080 プレビューはコマ落ちしやすい | 無料 | 導入が最も楽。直公開は不可、VPN 必須 |
| **Parsec** | 良い（ゲーミング系の低遅延） | 無料 / 商用有 | 映像を見ながらの操作向き |
| **Moonlight + Sunshine** | 良い | 無料 | GPU エンコード前提。NVIDIA 環境と好相性 |
| **AnyDesk / TeamViewer** | 中程度 | 商用ライセンス要 | 導入が簡単 |
| **VPN（Tailscale / WireGuard）＋ 上記** | — | 無料〜 | **ポート開放不要。セキュリティ上これが前提** |

### 7.2 検討事項

- **プレビュー品質**: 本アプリは 1080 動画をリアルタイム描画する。標準 RDP では大きくコマ落ちする。
  → プレビュー解像度 / フレームレートを落とすか、Parsec 系を使う
- **ShuttlePRO v2（USB HID）**: 手元の ShuttlePRO は**リモート先PCには刺さらない**。
  ただし送出タブは**キーボードショートカットが実装済み**（Space / Enter / Esc / A・D / W・S / N・P / 1〜4）なので、
  **ShuttlePRO を使わない運用ならリモートデスクトップだけで完結する**
- **現場側の無人化**: 自動ログオン、アプリの自動起動、停電復帰時の自動起動、UPS
- **セキュリティ**: RDP をインターネットに直公開しない。VPN 必須
- **モニタ構成**: 現場PCがヘッドレスだと解像度が変わる。ダミー HDMI プラグ or 仮想ディスプレイを付ける
- **音**: リモート側で音を確認する必要があるか

### 7.3 現実解（組み合わせ）

> **操作 = リモートデスクトップ（VPN 経由）＋ 確認映像 = 低ビットレートの SRT 1 系統**

RDP でプレビューが潰れる問題を SRT の確認用ストリームで補い、本線 SDI には手を入れない。
**実装コスト・機材コスト・リスクのいずれも最小。**

## 8. 進め方（段階導入）

| Step | 内容 | 判定基準 |
|---|---|---|
| 1 | 用途・許容遅延・回線を確定 | 「確認用」か「本線」かを決める |
| 2 | 機材選定（デモ機を借りて社内 LAN で疎通） | 絵が出る / フォーマットが崩れない |
| 3 | LAN 内で遅延・画質を実測、アプリと接続 | 軌道の細線が潰れないビットレートを確定 |
| 4 | 本番想定回線（インターネット / モバイル）でロス・遅延を実測 | latency 設定値の決定 |
| 5 | 断・復旧試験（ケーブル抜き、回線断） | アプリのフォールバック挙動を確認 |
| 6 | リモートデスクトップ検証（VPN ＋ RDP / Parsec） | オペレータが実運用速度で操作できるか |
| 7 | 本番リハーサル | — |
